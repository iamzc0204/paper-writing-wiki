# 一次實際執行後的反思

## 本次哪個節點最常卡關？

本次初版執行 records/run-v1.json 中，來源取得九份全部成功，Wiki 編譯、十八次查詢與簡報主張對應亦完成；最後內容檢查攔下兩項尚未完成的來源範圍判讀，均屬 source-scope 節點。

R01 是摘要篇幅：MIT 的教學建議不能直接視為所有投稿場合的字數規定。R02 是引用文獻類型：一般寫作教學對會議論文的評價，不能直接改成資訊領域的引用通則。這兩項是初版的待判讀項目，不是網路下載或模型 API 發生兩次崩潰。

## 檢查移到哪裡？

v1 在 Wiki 查詢與投影片分鏡完成後才檢查這些項目。v2 將「來源的適用範圍」移到 ingest 後、建立 Wiki 索引前。未完成判讀就停止，不讓候選規則進入可使用的知識。

## workflow / graph 如何修改？

v1：取得資料、整理 Wiki、查詢 Wiki、撰寫分鏡、最後檢查。

v2：取得資料、來源範圍判讀、整理 Wiki、查詢 Wiki、撰寫分鏡、主張核對、產生 HTML、檢查頁面。

來源問題回到原文與範圍判讀；投影片缺依據回到 Wiki 查詢；畫面問題只回到排版。這樣可避免每次都重做整份內容。兩項判讀的處理與依據保存在 content/scope-review.json，初版則保留在 records/scope-review-v1.json。

語意判讀由本次對話的 LLM 完成；程式確認判讀已完成、來源存在與主張對應，並保存實際執行時間及結果。本次觀察只比較這一份初版被攔下的項目數。

## 第二次檢閱後又改了什麼？

本輪以刻意改動的測試複本驗證檢查能力：保留主張編號，只更換查詢包文字。原版仍回報零項錯誤，顯示「編號存在」不足以確認內容一致。這項實驗及原檔還原結果保存在 records/review-baseline.json。

v3 在 HTML 產出前加入 Wiki 與查詢定義的版本核對，逐筆比對查詢包的主張全文、來源及定位；投影片改寫後，既有語意判讀也會失效，需重新核對。六項檢查實驗全部符合預期，包含正常內容、過期文字、過期 Wiki、錯誤引用、過期語意判讀及尚未完成的來源範圍判讀。這些是刻意設定的檢查案例，與初版兩項來源判讀分開記錄。

教學面也補上四項學習目標、八個概念頁的完成標準及完整摘要；模型比較事前訂定0.5個百分點門檻，讓下降0.2個百分點的示例結果能明確回答研究問題。第4、6頁的引用與第14頁的段落來源亦已讀回原文調整。
